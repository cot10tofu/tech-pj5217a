# Tinkとは？

Tinkは、Googleの暗号の専門家が作った「間違えにくい暗号ライブラリ」です。暗号のアルゴリズムを新しく作るものではありません。既存の暗号処理の上に、普通の開発者でも安全に使えるようにする層をかぶせたものだと考えると分かりやすいです。

## そもそも何のためにあるのか

Googleは開発の動機をこう説明しています。暗号では小さなミスが重大な結果につながり、正しく実装するには数十年分の学術文献を理解する必要がある。そんな時間のある開発者はほとんどいない。

そこで安全で、正しく使いやすく、誤用しにくい暗号APIを提供することを目標にしています。READMEでは、暗号を使うことが「暗闇でチェーンソーをジャグリングする」ようであってはならない、という趣旨の言い方をしています。

ポイントは、暗号が「動くのに安全ではない」状態を作りやすい分野だということです。普通のバグはテストで見つかります。暗号の誤りは、暗号化も復号も正常に動いてしまうので、攻撃されるまで誰も気づきません。

## Tinkを使わないと何が大変か

OpenSSLやJavaの標準暗号APIを直接使うと、開発者が次のようなことを自分で判断しなければなりません。

- **アルゴリズムとモードの選択**:AES一つ取っても、ECB、CBC、CTR、GCMなどのモードがあります。ECBのように、選んだ時点で危険なものも普通に使えてしまいます。
- **IV/ノンスの管理**:同じ鍵で同じノンスを再利用すると、GCMなどは安全性が根本から崩れます。Tinkはノンスの再利用で安全でなくなる方式では、利用者にノンスを渡させない設計です。
- **改ざん検知の付け忘れ**:暗号化しただけだと、中身は読めなくても書き換えられることがあります。正しく組み合わせないとパディングオラクル攻撃などを受けます。
- **暗号文のフォーマット設計**:IV、暗号文、認証タグをどの順に並べるか、どの鍵で暗号化したかをどう記録するか。チームごとに独自形式ができがちです。
- **鍵のローテーション**:鍵を新しくした後も、古いデータは古い鍵で復号できなければなりません。これを後から設計するのはかなり大変です。
- **鍵の保管**:鍵を設定ファイルやソースに平文で置いてしまう事故がよく起きます。
- **ライブラリ自体の落とし穴**:TinkはBoringSSLやJava Cryptography Architectureなど既存ライブラリの上に作られていますが、Project Wycheproofが見つけたそれらの弱点への対策も含んでいます。

つまり、素のライブラリは部品をくれるだけで、安全な組み立て方は利用者まかせです。

## Tinkを使うメリット

**1. 目的ベースのAPI。** 「AES-GCMで、IVは12バイトで…」とは考えません。「改ざん検知つきで暗号化したい(AEAD)」「署名したい」のように目的で選びます。APIは基本的に`encrypt`と`decrypt`だけです。中身の方式は、専門家が安全だと判断した鍵テンプレートから選ぶので、危険な組み合わせはそもそも選べません。

**2. 鍵のローテーションが最初から組み込まれている。** Tinkは鍵を単体ではなく「キーセット」(複数の鍵の束)として扱います。暗号文の先頭には、どの鍵で暗号化したかが記録されます。新しい鍵を追加して「主鍵」に切り替えれば、新しいデータは新しい鍵で暗号化され、古いデータもそのまま復号できます。自前でやると一番面倒な部分がほぼ自動になります。

**3. KMSとの連携。** AWS KMSやGoogle Cloud KMSなどの鍵管理サービスと組み合わせて、エンベロープ暗号化を簡単に実現できます。キーセットはKMSで暗号化して保存するのが標準の流れなので、鍵を平文で置く事故を防ぎやすくなります。

**4. 複数言語で互換性がある。** Java/Android、C++、Go、Pythonなどに対応しています。たとえばJavaのサーバーで暗号化したものをGoで復号する、といったことが同じ形式でできます。

**5. 実績。** Google社内の標準暗号ライブラリの一つで、数百のプロダクトやシステムで使われています。AdMob、Google Pay、Google Assistant、Firebaseなどのデータ保護にも使われています。

## 導入前に知っておきたい注意点

- **TLSのような通信プロトコルを作る道具ではありません。** アプリケーション内でデータを暗号化・署名する用途向けです。
- **何でもできるわけではありません。** 危険なアルゴリズムやモードはわざと用意されていないので、既存システムの独自形式と互換を取る用途には向かないことがあります。
- **暗号文はTink独自の形式です。** 鍵IDのプレフィックスが付くので、Tinkなしで復号する前提のデータには注意が必要です。
- **言語ごとに成熟度に差があります。** 昔はJavaScript版がアルファ扱いでした。現在のリポジトリはgithub.com/tink-crypto に移っていて、旧リポジトリは読み取り専用です。使う言語の状況は導入前に確認してください。
- **キーセットやプリミティブなどの独自概念は、最初に少し学ぶ必要があります。**

## 検討の目安

アプリケーションで次のようなことをしたいなら、Tinkは有力な選択肢です。

- 個人情報やトークンをDBに暗号化して保存する
- データに署名する
- 鍵を定期的に更新する運用を最初から考えておく
- チームに暗号の専門家がいない

逆に、既存の暗号仕様に厳密に合わせる必要がある場合や、TLSのような通信路の暗号化が目的の場合は、別の手段が向いています。

一言でまとめると、Tinkは「安全な選択肢しか選ばせず、鍵の運用まで含めて面倒を見てくれる暗号ライブラリ」です。
