# Tink × Cloud KMS：「キーセットを KMS で暗号化して保存する方式」によるクライアントサイド暗号化 解説

> **対象読者**：Google Cloud 上のアプリで、DB に保存するデータをアプリ側で暗号化したい開発者・アーキテクト
> **前提**：Tink の概要と、エンベロープ暗号化（DEK / KEK）の基本的な考え方は知っている
> **この資料の範囲**：方式の全体像、キーセットと DEK の考え方、DEK と KEK のローテーション、運用上の注意点（実装コードは扱いません）

---

## 0. 要点（3分で読む版）

- アプリが使う **DEK（データ暗号鍵）を「キーセット」という束にまとめ**、そのキーセットを **Cloud KMS の KEK（鍵暗号鍵）で暗号化して保存**する方式です。
- アプリは**起動時に1回だけ KMS を呼んで**キーセットを復号し、その後は**KMS を呼ばずにローカルで**データを暗号化・復号します。
- **DEK はデータごとに作りません。** キーセット内の「主鍵」1本で新しいデータを暗号化し、他の鍵は過去データの復号用です。
- **DEK は定期的にローテーションします**（新しい鍵を追加して主鍵に切り替える）。古い鍵は過去データの復号に必要なので残します。
- **古い DEK を削除せず、キーセットの鍵が少しずつ増えていく運用は一般的で、問題ありません。** Tink も Cloud KMS も、ローテーション時に古い鍵を自動で消さない設計です。
- **KEK は Cloud KMS で自動ローテーション**し、その後キーセットを新しい KEK バージョンで暗号化し直します。DB のデータには触れないので低コストです。
- 運用で最も重要なのは「**キーセットと KEK を絶対に失わないこと**」です。

## 1. 全体のアウトライン

### 1.1 登場するもの

| 名前 | 何か | どこにあるか |
|---|---|---|
| **KEK**（Key Encryption Key） | キーセットを暗号化する鍵。Cloud KMS の鍵 | Cloud KMS の中。**外に出ない** |
| **キーセット** | DEK の束（1本以上）。どれが主鍵か、各鍵の状態などの情報を持つ | 暗号化された状態で保存（Secret Manager、Cloud Storage、DB など任意） |
| **DEK**（Data Encryption Key） | 実際のデータを暗号化する鍵（例：AES-256-GCM） | キーセットの中。平文で存在するのはアプリのメモリ上だけ |
| **Tink** | キーセットの生成・暗号化・読み込み、データの暗号化・復号を担うライブラリ | アプリに組み込む |
| **Tinkey** | キーセットを操作するための Tink 公式コマンドラインツール | 運用担当者の手元や CI |

### 1.2 全体の流れ

```
【準備（最初に1回）】
  Cloud KMS に KEK を作成
        ↓
  Tink（または Tinkey）でキーセットを生成
        ↓
  キーセットを KEK で暗号化 → 「暗号化キーセット」として保存

【アプリ起動時（1回）】
  暗号化キーセットを読み込む
        ↓
  Cloud KMS に依頼してキーセットを復号（KMS 呼び出しはここだけ）
        ↓
  平文のキーセットをメモリに保持

【データ書き込み時（KMS 呼び出しなし）】
  平文データ ──[主鍵の DEK で暗号化]──→ 暗号文（先頭に鍵ID付き）──→ DB に保存

【データ読み込み時（KMS 呼び出しなし）】
  DB の暗号文 ──[先頭の鍵ID で DEK を選んで復号]──→ 平文データ
```

### 1.3 この方式を選ぶ理由（KMS Envelope AEAD 方式との比較）

Tink には、Cloud KMS を使ったクライアントサイド暗号化の方式が2つあります。

| 観点 | KMS Envelope AEAD 方式 | **キーセットを KMS で暗号化する方式（本資料）** |
|---|---|---|
| DEK の単位 | 暗号化1回ごとに新しい DEK | キーセット内の少数の DEK を共有 |
| KMS 呼び出し | **暗号化・復号のたびに毎回** | **起動時などに1回** |
| レイテンシ・コスト | 件数に比例して増える | ほぼ一定 |
| 使える暗号機能 | AEAD のみ | AEAD 以外（決定的暗号化、MAC、署名など）も可 |
| 暗号文のサイズ | ラップ済み DEK を含むので大きい | 先頭5バイトの鍵ID＋暗号データ |
| 1本の鍵が守る範囲 | 1件分 | キーセットの全データ |
| データ単位で鍵を消して読めなくする（クリプトシュレッディング） | しやすい | しにくい |

**DB のレコードを大量・高頻度に暗号化・復号するアプリ**では、KMS 呼び出しの回数がレイテンシ、コスト、KMS のクォータに直結します。そのため本方式が有力な候補になります。

## 2. キーセットとは

### 2.1 キーセットの中身

キーセットは複数の鍵をまとめた入れ物で、各鍵には次の情報があります。

| 項目 | 説明 |
|---|---|
| **鍵ID** | 4バイトの識別子。キーセット内で重複しないように振られる |
| **状態** | `ENABLED`（使用可）／`DISABLED`（一時停止。元に戻せる）／`DESTROYED`（鍵の中身を破棄済み。元に戻せない） |
| **鍵の種類** | 例：AES-256-GCM |
| **主鍵かどうか** | キーセット内で**主鍵は常に1本だけ** |

### 2.2 主鍵とそれ以外の役割分担

- **主鍵**：新しいデータの**暗号化**に使う
- **主鍵以外の `ENABLED` の鍵**：**復号専用**（過去に主鍵だった鍵など）

### 2.3 暗号文には「どの鍵で暗号化したか」が書かれている

標準の鍵テンプレート（例：`AES256_GCM`）で暗号化すると、暗号文の先頭に **5バイトのプレフィックス**が付きます。

```
[1バイト：バージョン 0x01] [4バイト：鍵ID] [IV] [暗号化データ] [認証タグ]
```

- 復号時、Tink はこの鍵IDを手がかりにキーセットから対応する DEK を選びます。
- プレフィックスは平文なので、**復号せずに「どの鍵で暗号化されたデータか」を集計できます**（第4章で活用）。
- このプレフィックスは認証されていない「ヒント」です。セキュリティ上の判断材料には使わないでください（どの鍵を使ったかの集計に使う分には問題ありません）。
- 鍵ID が付かない「RAW」形式のテンプレートもありますが、ローテーションの管理がしにくくなるため、**本方式では鍵IDつきの標準テンプレートを使うことを推奨**します。

### 2.4 なぜ DEK を複数持つのか

DEK を複数持てるのは、**時間とともに鍵を安全に入れ替えるため**です。データごとに鍵を分けるためではありません。

1. **ローテーション**：新しい鍵に切り替えても、古い鍵が残っていれば過去のデータを復号できる
2. **分散システムでの安全な切り替え**：新しい鍵を「主鍵ではない状態」で全サーバーに配ってから主鍵に昇格させれば、復号エラーを防げる
3. **アルゴリズムの移行**：種類の違う鍵を同じキーセットに入れられるので、方式の移行も同じ仕組みで行える
4. **侵害時の対応**：疑わしい鍵を主鍵から外し、段階的に無効化・破棄できる

> キーセットを作った直後は DEK が1本だけ、というのが普通です。鍵はローテーションのたびに1本ずつ増えていきます。

## 3. DEK のローテーション

### 3.1 ローテーションとは

キーセットに**新しい鍵を追加して主鍵に切り替える**ことです。Tink の標準的なローテーション操作では、**それまで主鍵だった鍵は `ENABLED` のまま残ります**。

```
ローテーション前： [鍵A（主）]
ローテーション後： [鍵A, 鍵B（主）]
                     ↑ 鍵Aは復号用として残る
```

- 新しいデータ → 鍵B で暗号化
- 既存のデータ → 鍵A のまま。**再暗号化は不要**で、そのまま復号できる

### 3.2 なぜローテーションするのか

| 理由 | 説明 |
|---|---|
| **これから書くデータを守る** | ある時点で鍵が漏れても、ローテーション後のデータは新しい鍵で守られる |
| **1本の鍵の使用量を抑える** | AES-GCM のようにランダムな IV を使う方式は、1本の鍵で安全に暗号化できる回数に実用上の上限がある（NIST SP 800-38D に基づき、目安は約 2³² 回）。書き込みが多いシステムほど重要 |
| **コンプライアンス・監査** | PCI DSS など、鍵の定期的なローテーションを求める基準がある |
| **緊急時に備える** | 普段から回しておけば、侵害時にも同じ手順で迅速に切り替えられる |

### 3.3 頻度の考え方

- **期間で決める**：例えば年1回、または90日ごと。監査要件があればそれに合わせる
- **使用量で決める**：書き込みが非常に多い場合は、暗号化回数が上限の目安に近づく前に切り替える
- **イベントで決める**：鍵の漏洩が疑われたときは、定期のローテーションとは別に即座に実施する

### 3.4 分散環境での安全な手順

複数のアプリインスタンスが同じキーセットを使う場合、**いきなり新しい鍵を主鍵にしない**ことが重要です。まだ新しい鍵を知らないインスタンスが、新しい鍵で暗号化されたデータを復号できなくなるからです。

```
ステップ1：新しい鍵を「主鍵ではない状態」で追加し、保存・配布
           → 全インスタンスが新しい鍵を「復号できる」状態になる
ステップ2：全インスタンスに行き渡ったことを確認
ステップ3：新しい鍵を主鍵に昇格し、保存・配布
           → 新しいデータは新しい鍵で暗号化される
```

> アプリは起動時にキーセットを読み込むため、更新したキーセットを反映するには**再起動か定期的な再読み込み**の仕組みが必要です。

### 3.5 古い DEK は消さずに増え続ける運用が一般的

**DB の永続データを暗号化する用途では、古い DEK を削除せず、キーセットの鍵が少しずつ増えていく運用が一般的で、それで問題ありません。**

#### なぜそれでよいのか

| 観点 | 説明 |
|---|---|
| **製品の設計がそうなっている** | Tink のローテーションは古い主鍵を `ENABLED` のまま残します。Cloud KMS も、ローテーションで古い鍵バージョンを自動で無効化・破棄しません。古い鍵を残すのが標準の挙動です |
| **増え方がとてもゆっくり** | 年1回のローテーションなら10年で約10本。90日ごとでも10年で約40本 |
| **性能に影響しない** | 復号時は暗号文の鍵IDで対象の鍵を直接選ぶので、鍵が増えても遅くならない |
| **サイズも問題にならない** | 鍵1本あたりのデータはごく小さく、キーセット全体も小さいまま |
| **ローテーションの主な効果は削除しなくても得られる** | 新しいデータの保護と、1本あたりの使用量の制限は、古い鍵を残していても有効 |
| **一度書いたら更新しないデータと相性がよい** | 古い鍵で暗号化されたデータを無理に移行する必要がない |

#### 受け入れることになるリスク

- 万一**平文のキーセットが漏れると、過去すべてのデータ**が読める状態になる
  → ただし平文のキーセットはアプリのメモリ上にしかなく、保存時は KEK で暗号化されています。実際の防御の中心は「**Cloud KMS の KEK を誰が使えるか（IAM）**」です。
- 鍵を削除してデータを確実に読めなくする**クリプトシュレッディングが使えない**
  → 保持期限が過ぎたデータを鍵の削除で消したい要件がある場合は、別途設計が必要です（3.7 を参照）。

#### 増え続ける運用で守るべきこと

1. **DEK のローテーション自体は続ける**（増えるのが嫌だからといって止めない）
2. **鍵ID つきの標準テンプレートを使う**（いざというときに「どのデータがどの鍵か」を特定できるようにするため）
3. **キーセットを絶対に失わない**（第5章）
4. **KEK のローテーションを行う**（第4章）

### 3.6 やってはいけない：固定数の鍵を巡回させる

「鍵は数本でいいなら、最初に数本作って順番に主鍵を回せばよいのでは」と考えるかもしれません。Tink の API 上は可能ですが、**推奨されません**。

| 問題 | 説明 |
|---|---|
| 漏洩時の被害が限定されない | 漏れた鍵の順番が再び回ってくると、将来のデータも危険にさらされる |
| 漏れた鍵を捨てられない | 巡回中の鍵にはどれも使用中のデータがあるため削除できない |
| 使用量が積み上がる | 巡回のたびに、1本あたりの暗号化回数が増え続ける |
| 監査で認められにくい | 同じ鍵に戻る運用は、ローテーションとはみなされない可能性が高い |

> 正しいイメージは「**鍵が増えていく**」こと、または「**新しい鍵を足し、不要になった古い鍵を消すスライディングウィンドウ**」です。一度主鍵でなくなった鍵を、再び主鍵に戻すことはしません。
> なお、**次の鍵を1本だけ先に作り、主鍵ではない状態で配っておく**のは 3.4 の手順そのもので、良い習慣です。

### 3.7 （参考）古い DEK を削除したくなった場合

通常は不要ですが、侵害対応や保持期限の要件などで古い DEK を消したい場合の考え方です。

**前提**：その鍵で暗号化されたデータが**どこにも残っていない**こと。

1. **残っているか調べる**：暗号文の先頭5バイトから鍵ID を取り出し、DB で鍵ID ごとの件数を数える。書き込み時に鍵ID を別の列に保存しておくと、インデックスが張れて楽になる
2. **再暗号化する**：古い鍵のデータを読み出し、現在の主鍵で暗号化し直す（書き込み時に順次移す方法と、バッチで移す方法がある）
3. **DB の外も確認する**：バックアップ、スナップショット、レプリカ、BigQuery などへのエクスポート、キャッシュ、他のサービスへのコピー
4. **まず `DISABLED` にする**：しばらく運用し、復号エラーが出ないことを確認する（出たら `ENABLED` に戻せる）
5. **バックアップの保持期限を待ってから `DESTROYED` にする**

> Tink は「古い鍵のデータが残っているか」を自動では判断しません。上記のように**自分たちで数えて判断**します。最も見落としやすいのは DB の外にあるコピーです。

## 4. KEK（Cloud KMS の鍵）のローテーション

### 4.1 必要か？

**技術的には必須ではありませんが、推奨します。** Google Cloud も対称鍵の定期的な自動ローテーションを推奨しています。

本方式では、KEK のローテーションによる**安全性の向上は限定的**です。

- KEK は Cloud KMS の外に出ないので、もともと漏洩のリスクが低い
- KEK が暗号化するのはキーセットだけなので、使用量の上限を気にする必要がない

それでも行う理由は次のとおりです。

- **コンプライアンス・監査**：「すべての鍵に使用期限がある」と説明できる
- **ほぼ無料**：Cloud KMS の自動ローテーションを設定するだけ
- **緊急時に備える**：手順を普段から回しておける

### 4.2 仕組みと注意点

| ポイント | 説明 |
|---|---|
| ローテーションで起きること | Cloud KMS に新しい鍵バージョンが作られ、主バージョンになる |
| 古いバージョン | **自動では無効化・破棄されない**。Cloud KMS の暗号文にはバージョン情報が含まれるので、古いバージョンで暗号化したキーセットもそのまま復号できる |
| **ローテーションだけではキーセットは更新されない** | 保存済みのキーセットは古いバージョンで暗号化されたまま。効果を得るには、**キーセットを読み込み、新しいバージョンで暗号化し直して保存する**作業が必要（DB のデータには触れない） |
| 古いバージョンの破棄 | **すべてのキーセットを暗号化し直したことを確認してから**行う。Cloud KMS の破棄は予約制で、デフォルトでは30日間の猶予期間があり、その間は復元できる。ただし猶予期間に頼らず、事前に `無効化` して影響がないことを確かめる |

### 4.3 推奨構成

1. Cloud KMS の KEK に**自動ローテーション**を設定する
2. ローテーション後に、**キーセットを新しい KEK バージョンで暗号化し直す定期ジョブ**を用意する
3. 古い KEK バージョンは、全キーセットの更新を確認してから無効化し、十分な期間をおいてから破棄する（あるいは破棄せず無効化のまま残す）

### 4.4 DEK と KEK のローテーション比較

| | DEK のローテーション | KEK のローテーション |
|---|---|---|
| 対象 | キーセット内の鍵 | Cloud KMS の鍵バージョン |
| 守るもの | DB のデータそのもの | キーセット |
| 安全性への効果 | 中（新しいデータの保護、使用量の制限） | 小（KEK が KMS の外に出ないため） |
| 作業 | 鍵の追加 → 配布 → 主鍵への昇格 | 自動ローテーション → キーセットの暗号化し直し |
| DB のデータへの影響 | なし（再暗号化は不要） | なし |
| 古い鍵の扱い | 残す（増え続けてよい） | 全キーセットの更新後に無効化・破棄してよい |

## 5. 運用上の重要ポイント

### 5.1 最重要：キーセットと KEK を失わない

古い DEK を残す運用では、**キーセットが全期間のデータを復号するための唯一の手段**になります。

- **キーセットの保存先を冗長化し、バックアップを取る**（例：Secret Manager のバージョン管理、複数リージョンでの保存）
- **キーセットの更新手順を間違えない**：ローテーションのたびにキーセットを書き換えるので、上書きミスで古い鍵を失わないよう、レビューやバージョン管理、ロールバック手段を用意する
- **KEK の鍵バージョンを誤って破棄しない**：キーセットを復号できなくなると全データが読めなくなる。破棄の権限は厳しく絞る

### 5.2 IAM（アクセス権）の設計

- キーセットを復号できる（KEK の `Decrypt` 権限を持つ）のは、**本番アプリのサービスアカウントだけ**にする
- 鍵を管理する権限（ローテーションや破棄）と、鍵を使う権限（暗号化・復号）は分ける
- 平文のキーセットを人が扱う場面をなくす（Tinkey も KMS 連携モードで使う）

### 5.3 関連データ（AAD）の活用

- **データの暗号化**：レコードID やテナントID などを AAD に含めると、暗号文を別のレコードに付け替える攻撃を防げる
- **キーセットの暗号化**：キーセットを KEK で暗号化するときにも AAD を指定できる。用途や環境を表す値を入れておけば、別の用途のキーセットとの取り違えを防げる

### 5.4 監査ログの粒度

- Cloud KMS の監査ログに残るのは「**キーセットを復号した**」記録だけで、**どのレコードを復号したかは残りません**
- レコード単位の監査が必要なら、**アプリ側で復号のログ**（誰が、どのレコードを）を記録する

### 5.5 平文の扱い

- 復号したデータや平文のキーセットを、**ログ、例外メッセージ、デバッグ出力に出さない**

### 5.6 いざというときに再暗号化できる余地を残す

- 普段は再暗号化しなくても、**鍵ID の集計方法**と**再暗号化バッチの設計**を用意しておくと、侵害時の対応が大きく変わる

---

## 6. この方式が向いているケース・向いていないケース

### 向いている
- DB のレコードを大量・高頻度に暗号化・復号する
- KMS の呼び出し回数（レイテンシ・コスト・クォータ）を抑えたい
- AEAD 以外の暗号機能（決定的暗号化による検索、MAC など）も使いたい
- 一度書いたら更新しないデータが多い

### 慎重に検討が必要
- **データ単位やユーザー単位で鍵を消して読めなくする**（クリプトシュレッディング）要件がある
  → テナントごとにキーセットを分ける、または KMS Envelope AEAD 方式を検討する
- **レコード単位の KMS 監査ログ**が規制上必須である
  → KMS Envelope AEAD 方式なら、暗号化・復号のたびに KMS の記録が残る
- **平文のキーセットがアプリのメモリ上にあること**自体が許容できない

## 7. 用語集

| 用語 | 意味 |
|---|---|
| DEK | Data Encryption Key。データを暗号化する鍵 |
| KEK | Key Encryption Key。鍵を暗号化する鍵。本方式では Cloud KMS の鍵 |
| キーセット | Tink が扱う鍵の束。主鍵1本と、復号用の鍵からなる |
| 主鍵（primary） | キーセット内で新しいデータの暗号化に使う鍵 |
| 鍵ID | キーセット内の各鍵を識別する4バイトの値。暗号文の先頭に付く |
| 暗号化キーセット | KEK で暗号化されたキーセット。保存・配布する形 |
| AEAD | 改ざん検知つきの暗号化（Authenticated Encryption with Associated Data） |
| AAD | AEAD で暗号文に結び付ける「関連データ」。暗号化はされないが、改ざんや取り違えを検知できる |
| ローテーション | 新しい鍵を作って切り替えること |
| クリプトシュレッディング | 鍵を破棄して、その鍵で暗号化したデータを読めなくすること |
| Tinkey | キーセットを操作する Tink 公式のコマンドラインツール |

---

## 8. 必要な運用

この方式に特有の運用だけを挙げます（復号エラーの監視や IAM の見直しなど、どの暗号化方式でも共通の運用は除いています）。古い DEK は削除しない前提です。

**DEK のローテーション（年1回〜90日ごと）**
- 新しい鍵を主鍵にせずに追加し、キーセットを保存する
- キーセットを使う全インスタンスへの反映を確認する
- 新しい鍵を主鍵に昇格し、キーセットを保存する

**KEK ローテーション後の後処理（要件がある場合）**
- キーセットを新しい KEK バージョンで暗号化し直す（定期ジョブ）
- 全キーセットの更新を確認してから、古い KEK バージョンを無効化・破棄する

**キーセットの管理**
- 暗号化キーセットの保存先とバージョン管理（Secret Manager など）
- キーセットのバックアップ（失うと全期間のデータを復号できなくなる）
- アプリがキーセットを再読み込みする仕組みと、反映時間の保証

**監査（要件がある場合）**
- レコード単位の復号ログをアプリ側で記録する（KMS の監査ログにはキーセットを復号した記録しか残らないため）
